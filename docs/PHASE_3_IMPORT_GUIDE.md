# Phase 3 import operations

## Polling Forecast published models

`Import-PollingForecast.ps1 -Dataset senate` (or `house` / `governors`) makes one explicit HTTPS request, verifies the documented dataset, 2026 cycle, row count, CC BY 4.0 license, state/key match and probability bounds, and imports only the provider's forecasts. Set `ELECTION_DB_URL`, `ELECTION_DB_USER` and `ELECTION_DB_PASSWORD` for the intended local PostgreSQL database first; Flyway migrates that database. The script builds in an isolated output folder. It does not import any third-party survey figures, run in demo mode, automatically poll the source or modify a different database.

The provider's date-only `asOf` is stored as a date, not an invented timestamp. `asOf` timestamp queries exclude such records because their publication time cannot be established. The displayed probability is explicitly the publisher's estimate for its listed left candidate; it is not an internal model, vote share or a race call. Source race keys are namespaced provider identities, not verified canonical race mappings. Margin and uncertainty fields are margins, so they are not imported into vote-share interval fields. Raw payload bytes and SHA-256 are archived; changed rows produce new snapshots, identical imports are idempotent. HTTP errors, including 429, stop the manual import and report Retry-After; there is no unattended scheduler or automatic retry. The source currently documents a ten-minute cache and 120 requests per minute; keep manual use well below that limit. Recheck terms before reuse.

## Individually licensed surveys

Before `Publish-LicensedSurvey.ps1 -SourceFile <file>`, a responsible operator must independently review the rights for the individual publication and configure its matching `polling_providers` and `polling_sources` records, including the exact provider ID, source ID, HTTPS publication URL, license ID, attribution, rights evidence, approval timestamp and redistribution permission. The application provides no public approval or write endpoint. Database approval is an operator attestation, not automated proof of rights. Explicit test-marked input is rejected; never mark fictional content as real.

The UTF-8 JSON document must contain `isTestData: false`, `providerId`, `sourceId`, `publicationUrl`, `licenseId` and exactly one object in `records`. That survey requires `kind: survey`, `year`, `office`, optional state and House district, `pollster`, `sponsor`, `questionIdentity`, `matchupIdentity`, `population`, `fieldStart`, `fieldEnd`, an offset-qualified `publishedAt`, `providerPollId`, `providerRevision`, and at least one answer with `choiceId`, `label` and nullable percentage. Optional `sampleSize`, `surveyMode`, `marginOfError` and answer `candidateId` are preserved. Identities must represent actual source questionnaires and matchups; the importer cannot independently establish that they are truthful.

The transaction serializes imports, rejects unapproved sources and conflicting revision reuse, archives input by SHA-256, and checks pollster, sponsor, scope, field dates, population, questionnaire, matchup, sample, method and answer identities. A matching syndicated publication attaches to one canonical survey and keeps its own citation. Ambiguous identities, multiple matches, conflicting methods or answer choices stop for review. Different questionnaire versions remain separate. The public API returns a survey once and lists approved citations, honoring the as-of cutoff. This is conservative matching, not a guarantee against false identifiers or incorrect operator-provided metadata. No reviewed real survey was supplied or imported.

The older `Import-Polls.ps1` only stages a file and does not publish it. New scripts require local PostgreSQL credentials and do not use demo fixtures. Sample test documents are used solely in disposable integration databases.
